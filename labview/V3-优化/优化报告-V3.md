# V3 优化报告：把「查表」改成「译码」

> 对象：`V3-优化/十字路口仿真V3.0.vi`（由 V2 复制而来）
> 基准（唯一真值）：`V2-功能实现/完整灯态逐秒表.csv`（175 秒 × 12 灯组）
> 验证脚本：`V3-优化/verify_phase_model.py`（已跑通，见第 2.4 节）
> 编写日期：2026-11-17

---

## 0. 摘要：先给结论

**一句话**：V2 花 96 个格子 + 12 个索引数组 + 28 个 `等于?` 来点灯；V3 只要 **8 个 `等于?` + 4 个 `或` + 8 个 `非`（共 20 个逻辑节点、8 个数值常量、一格表都不用填）**，输出的 28 个布尔与基准表 **2100 个值逐值一致**。

**为什么能砍这么多**：那张 8 行 × 12 列的表里，**83.3% 的格子是 0**，12 列其实只有 **8 种**不同图样，而且每个灯组的非零只落在**一对**相邻的时间片上。也就是说，这张"表"真正的信息量只有「**12 个灯组各归属哪一对片**」+「**每对片里第一片绿、第二片黄**」。把这件事直接写成逻辑，表就没有存在的必要了。

**三个想法的处置**：

| 你的想法 | 结论 | 说明 |
|---|---|---|
| ① 数组优化（数字电路思路） | **采纳，作为 V3 主线** | 表 → 3 位状态码的最小项译码，逻辑节点 40 → 20 |
| ② 底层重写 | **采纳，是唯一剩下的改进（V3.2）** | 查表法 → 状态机法（`i` + `sec` 两个状态 + `DUR` 时长表）。V3.1 已验收通过，前提满足；设计已用 `verify_state_machine.py` 验证（2625 个值全一致） |
| ③ 更方便的控件 | **不做（控件改造不单独设期）** | 打包 28 只灯成簇/数组要多 13 个节点、接线端子从 28 涨到 36，省的是面板控件数、花的是框图连线；剩下的档位/复位属演示便利，不影响正确性。理由压缩到第 5 节 |

**优化前后（同一功能）**：

| 指标 | V2 / V3.0 | V3.1（本报告推荐） | 变化 |
|---|---|---|---|
| `COLOR` 表格子 | 96 | **0** | 全删 |
| 要手填的数字/字符串 | 约 162 | 约 34 | **−79%** |
| 索引数组节点（`COLOR` 专用） | 12 | 0 | 全删（另 3 个查 `START`/`END`/`NAME` 的保留） |
| `等于?` 节点 | 28 | 8 | −71% |
| 逻辑节点合计 | 40 | **20** | **−50%** |
| 从 `COLOR` 扇出的 `s0…s11` 长线 | 12 根 | 0 根 | 全删 |
| 拼错一格就坏一只灯的位置 | 96 处 | **0 处** | 隐患消失 |
| 逐秒对照 | 通过 | 通过（等价性已证） | 不变 |

## 1. 现状盘点：V2/V3.0 由什么构成

先把要优化（和不该动）的东西分清楚。

### 1.1 结构清单

| 层 | 元件 | 数量 | 作用 |
|---|---|---:|---|
| 数据 | `START` | 8 | 每秒扫表用：各片起始秒 |
| 数据 | `END` | 8 | 剩余秒显示用 |
| 数据 | **`COLOR`** | **96 格** | 片号 → 12 组灯态（0 红／1 绿／2 黄） |
| 数据 | `NAME` | 8 串 | 片号 → 片名 |
| 数据 | `CYCLE` / `N` | 2 | 周期 175 / 片数 8 |
| 时序 | While + 等待 + `加` + `商与余数` | — | 1 s 节拍、t 自增取模 |
| 时序 | For 循环 + `索引数组(START,i)` + `大于等于?` + `选择` | — | **扫表求当前片号 i** |
| 译码 | **12 个 `索引数组`（COLOR）** | 12 | 取 `s0…s11` |
| 译码 | **28 个 `等于?`** | 28 | `s==0/1/2` → 红/黄/绿 |
| 显示 | 28 个圆形指示灯 + 4 个数值/字符串 | 32 | 页②总表 + 页①灯头布局 |

### 1.2 真正的成本在哪：**手填数字的数量 = 出错面**

V2 要你手填约 **162** 个数字/字符串（8+8+96+8+1+1，再加 12 个列索引常量、28 个色值常量）。这 162 个位置里任意一个敲错，**程序照样能跑、断线检查也查不出来**，只会在某只灯上表现为"该亮不亮"。

这类错误有一个共同点：**属于"数据错"，不属于"逻辑错"**。断线箭头、`Ctrl+H`、错误列表一个都发现不了。所以优化的第一目标不是"少几个节点"，而是**让"要填的数字"少到不用查表**。

## 2. 关键发现：那 96 格表其实是空的

### 2.1 83.3% 的格子是 0

用基准表统计（`verify_phase_model.py` 第 1 段）：

| 值 | 格数 | 占比 |
|---|---:|---:|
| `0`（红） | 80 | 83.3% |
| `1`（绿） | 12 | 12.5% |
| `2`（黄） | 4 | 4.2% |
| 合计 | 96 | 100% |

**非零格只有 16 个。** 剩下 80 格的作用只是"声明这组灯此刻是红的"——而这其实可以由"不是绿也不是黄"推出来。

### 2.2 12 列只有 8 种图样

按列读出 8 个片的值，12 个灯组只有 8 种不同的图样：

| 图样（片 1→8） | 灯组 |
|---|---|
| `1 2 0 0 0 0 0 0` | `MV_NS_TH` |
| `0 0 1 2 0 0 0 0` | `MV_NS_LT` |
| `0 0 0 0 1 2 0 0` | `MV_EW_TH` |
| `0 0 0 0 0 0 1 2` | `MV_EW_LT` |
| `1 0 0 0 0 0 0 0` | `BK_NS_TH`、`PW_E`、`PW_W` |
| `0 0 1 0 0 0 0 0` | `BK_NS_LT` |
| `0 0 0 0 1 0 0 0` | `BK_EW_TH`、`PW_N`、`PW_S` |
| `0 0 0 0 0 0 1 0` | `BK_EW_LT` |

看第三行、第五行的图样重复就知道：**表里有大量冗余**，`PW_E` 和 `PW_W` 完全一样，`PW_N`、`PW_S` 和 `BK_EW_TH` 完全一样。

### 2.3 每个灯组只"归属"一对片

每组灯的非零只出现在一对相邻片上，而且**一绿一黄**：

| 灯组 | 非零片（0 基） | 几态 |
|---|---|---|
| `MV_NS_TH` | 片 0、1 | 红/黄/绿 |
| `MV_NS_LT` | 片 2、3 | 红/黄/绿 |
| `MV_EW_TH` | 片 4、5 | 红/黄/绿 |
| `MV_EW_LT` | 片 6、7 | 红/黄/绿 |
| `BK_NS_TH` | 片 0 | 红/绿 |
| `BK_NS_LT` | 片 2 | 红/绿 |
| `BK_EW_TH` | 片 4 | 红/绿 |
| `BK_EW_LT` | 片 6 | 红/绿 |
| `PW_N`、`PW_S` | 片 4 | 红/绿 |
| `PW_E`、`PW_W` | 片 0 | 红/绿 |

规律非常整齐：**片号是偶数 → 绿灯；片号是奇数 → 黄灯（只有机动车有）；其余全红。**

### 2.4 等价性证明（已跑通）

`verify_phase_model.py` 只用两样东西重算全部灯态：

1. 每组的"归属片号" `k`（上表）；
2. 规则：`i == k` → 绿；`i == k+1` 且是机动车 → 黄；否则红。

结果：

```
[2] 用「归属片号 + 奇偶黄灯」模型重算：2100 个值（175 秒 × 12 组）
    [通过] 全部一致 —— 96 格表可以用「12 个归属片号 + 1 条奇偶规则」完全替代。
```

**2100 个值零差异**。这条结论是整个 V3 的地基：删表不会丢功能。

### 2.5 换成数字电路的说法

把上面的事翻译成你熟悉的语言，优化思路就一目了然了：

- `i`（0…7）是一个 **3 位状态码**，8 个时间片就是 8 个**最小项**（minterm）；
- `COLOR` 表就是一张**真值表**（片号 × 灯组 → 灯态）；
- 现在这张真值表能做**卡诺图化简**，因为它的 1 分布极其稀疏、规整；
- 化简结果：

```
绿灯_k = E(2k)              k = 0,1,2,3   （4 个最小项）
黄灯_k = E(2k+1)            k = 0,1,2,3   （4 个最小项）
机动车红_k = ¬(E(2k) ∨ E(2k+1))        （与门/或非：一组两片都不亮就是红）
非机/行人红 = ¬E(2k)                    （两态：不绿就是红）
其中 E(n) = (i == n)
```

- **最漂亮的化简点**：`E(0)`、`E(2)`、`E(4)`、`E(6)` 这 4 个最小项**一个喂好几个灯组**：

| 最小项 | 直接驱动的灯（一线多连） |
|---|---|
| `E(0)` = `i==0` | `NS_TH_G`、`BK_NS_TH_G`、`PW_E_G`、`PW_W_G` |
| `E(4)` = `i==4` | `EW_TH_G`、`BK_EW_TH_G`、`PW_N_G`、`PW_S_G` |
| `E(2)` = `i==2` | `NS_LT_G`、`BK_NS_LT_G` |
| `E(6)` = `i==6` | `EW_LT_G`、`BK_EW_LT_G` |
| `E(1/3/5/7)` | 各自的机动车黄灯（1 对 1） |

所以：**8 个 `等于?` 就能生成全部 16 个"绿或黄"布尔**，红灯再取反即可。这就是 20 个节点点 28 只灯的来历。

## 3. 想法①：数组优化的三种实现

### 方案 A（推荐落地）：最小项译码

```
                    ┌── E0 = i==0 ──→ NS_TH_G / BK_NS_TH_G / PW_E_G / PW_W_G
                    ├── E1 = i==1 ──→ NS_TH_Y
                    ├── E2 = i==2 ──→ NS_LT_G / BK_NS_LT_G
   i ──(扇出 8 路)──┼── E3 = i==3 ──→ NS_LT_Y
                    ├── E4 = i==4 ──→ EW_TH_G / BK_EW_TH_G / PW_N_G / PW_S_G
                    ├── E5 = i==5 ──→ EW_TH_Y
                    ├── E6 = i==6 ──→ EW_LT_G / BK_EW_LT_G
                    └── E7 = i==7 ──→ EW_LT_Y

   机动车红：¬(E0∨E1)、¬(E2∨E3)、¬(E4∨E5)、¬(E6∨E7)   → 4 个「或」+ 4 个「非」
   非机/行人红：¬E0、¬E2、¬E4、¬E6                        → 4 个「非」（各喂 2~3 只灯）
```

- 节点：`等于?`×8 + `或`×4 + `非`×8 = **20**
- 常量：8 个（`0…7`，表示法设 I32）
- 表格：**0 格**

**优点**：节点最少、最容易搭、和"第几片"一一对应，改配时（只改秒数）完全不用动它。
**缺点**：`i` 的编码（偶数绿、奇数黄）是"约定"而不是"结构"，看代码要记住这条约定 —— 这一点方案 B 更好。

### 方案 B（理论最漂亮，写报告用）：状态编码 + 一热码

把 `i` 拆成 **相位位 p** 和 **黄灯位 y**：

```
p = i div 2   （0…3，四个相位）
y = i mod 2   （0=绿段，1=黄段）      ← 一个「商与余数」节点同时给出两个字
```

再用 4 个 `等于?(p,0..3)` 得到**一热码** `P0…P3`（相位译码器），然后：

```
绿_k = P_k ∧ ¬y          4 个「与」+ 1 个「非」
黄_k = P_k ∧ y           4 个「与」
机动车红 = ¬(绿∨黄)       4 个「或」+ 4 个「非」
```

- 节点：`商与余数`×1 + `等于?`×4 + `与`×8 + `非`×9 + `或`×4 = **22**（比方案 A 多 2 个）
- 好处：**"8 片 = 4 相位 × 2 子状态"这件事在框图里是看得见的**，和交通工程的"相位"术语对齐，写课程报告时特别好讲：
  > 8 个时间片并非 8 个独立状态，而是 4 个相位（南北直行／南北左转／东西直行／东西左转）× 2 个阶段（绿、黄），因此状态机可写成 2 位相位码 + 1 位阶段码。

**建议**：**框图按方案 A 搭，报告按方案 B 写**（两者功能等价，B 更好讲）。若你更愿意框图自解释，就用 B，多两个节点而已。

### 方案 C（不推荐做主方案）：位打包状态字

把每一片的 28 个灯压成一个 **U32**（28 位），8 片就是 8 个 U32 常量：
`S = 索引数组(STATE, i)` 一根线出来，每只灯 = `(S >> n) & 1`。

- 表格：8 个 U32（写成 16 进制很漂亮）
- 但每只灯要 `右移` + `与` + `判断非零` = 3 个节点 → **28×3 = 84 个节点**
- 且**常量是不可读的十六进制**，改一个灯要手算位——比 V2 填格子更容易错

**结论**：C 只适合做"状态字显示"（页③放个 U32 十六进制窗，写报告时很唬人），**不要用它驱动灯**。

### 三方案对比

| 指标 | A 最小项 | B 相位一热码 | C 位打包 |
|---|---:|---:|---:|
| 逻辑节点 | **20** | 22 | ~86 |
| 表格格数 | **0** | 0 | 8 个 U32 |
| 数值常量 | 8 | 5 | 8 |
| 可读性（新手） | 好 | 好（术语对齐） | 差 |
| 自解释状态编码 | 中 | **强** | 弱 |
| 改配时（改秒数） | 不用改 | 不用改 | 不用改 |
| 加/删相位 | 要改 | 要改 | 要改 |
| 建议 | **落地用** | 报告用/或落地 | 只做显示 |

## 4. 想法②：底层重写（查表法 → 状态机法）

### 4.1 现在的时间基准怎么工作

```
t ──(For 循环扫 8 片：t ≥ START[i]?)──→ i ──→ 译码 ──→ 灯
```

每秒扫一次 8 个起点，取"最后一个满足 `t ≥ START[i]` 的 i"。这是**纯函数**：给定 t 立刻得 i，没有记忆，所以复位、跳转都很容易。

### 4.2 状态机法：状态、时长表、转移规则

真实信号机不是"查表找我现在在哪片"，而是"**计时到点就推进到下一片**"。用两个整数就能描述完整：

```
状态：(i, sec)      i = 片号 0…7，sec = 本片已过秒数（0 … DUR[i]-1）
时长表：DUR = [46, 4, 26, 4, 60, 5, 25, 5]      ← 8 个数字
初值：(0, 0)

每拍（1 s）：
  n    = DUR[i]
  sec2 = sec + 1
  sec2 ≥ n ?  ──是──→  ( (i+1) mod 8 , 0 )      ← 本片放完，进下一片
              └─否──→  ( i , sec2 )             ← 本片继续
```

**时长表就是配时**：`46+4` 南北直行、`26+4` 南北左转、`60+5` 东西直行、`25+5` 东西左转，合计 175 s。它和 `START` 是同一件事的两种写法：`START[k] = DUR[0] + … + DUR[k-1]`（脚本已断言这条自洽关系成立）。

**状态转移表**（`verify_state_machine.py` 会打印，可直接照抄）：

| 当前片 | `DUR[i]` | `sec` 取值 | 何时推进 | 次态 |
|---|---:|---|---|---|
| 片1 | 46 | 0…45 | `sec+1 = 46`，即 `sec = 45` | 片2，sec=0 |
| 片2 | 4 | 0…3 | `sec = 3` | 片3，sec=0 |
| 片3 | 26 | 0…25 | `sec = 25` | 片4，sec=0 |
| 片4 | 4 | 0…3 | `sec = 3` | 片5，sec=0 |
| 片5 | 60 | 0…59 | `sec = 59` | 片6，sec=0 |
| 片6 | 5 | 0…4 | `sec = 4` | 片7，sec=0 |
| 片7 | 25 | 0…24 | `sec = 24` | 片8，sec=0 |
| 片8 | 5 | 0…4 | `sec = 4` | 片1，sec=0 |

**为什么是 `sec+1 ≥ n` 而不是 `>`**：片 1 要占满 `t = 0…45` 共 46 秒。进入片 1 时 `sec = 0`（对应 t=0）；每拍先算 `sec+1`，当 `sec+1 = 46` 时，说明**这一拍已经用掉第 46 秒**，下一拍该进片 2 —— 所以用 `≥`。写成 `>` 会让每片多站一秒，周期变成 183 s，`t=46` 还停在片 1。

**框图里是 7 个节点**（都在 While 内，原来的 For 循环整块不要了）：

| # | 节点 | 输入 | 输出 | 说明 |
|---|---|---|---|---|
| 1 | `索引数组` | `DUR`、`i` | `n`（本片时长） | |
| 2 | `加` | `sec`、`1` | `sec+1` | |
| 3 | `大于等于?` | `sec+1`、`n` | `推进?`（布尔） | 本方案唯一的比较 |
| 4 | `选择` | `s=推进?`、真=`0`、假=`sec+1` | `sec_next` | |
| 5 | `加` | `i`、`1` | `i+1` | |
| 6 | `商与余数` | `i+1`、`8` | 取**余数** = `i_wrap` | 取商会变成 `(i+1)/8`，永远 0 或 1 |
| 7 | `选择` | `s=推进?`、真=`i_wrap`、假=`i` | `i_next` | |

> ⚠️ **最要紧的一条接线约束**：第 4 号和第 7 号两个 `选择` 的 `s` 必须接**同一根** `推进?` 线。分开接（比如其中一个忘了连、或各自接了别的比较）就会出现"`sec` 归零了但 `i` 没变"，表现是**卡在某一秒反复闪**。

### 4.3 显示量怎么算：选"派生"最稳

状态机里不再有 `t` 这个变量，`t_s` 和 `remain_s` 要重新给。三种做法：

| 方案 | 保留的表 | 数值总数 | `t_s` | `remain_s` | 风险 |
|---|---|---:|---|---|---|
| **A 派生（推荐）** | `START` + `DUR` | 16 | `START[i] + sec` | `DUR[i] − sec` | **无**：t 是算出来的，不会和状态失步 |
| B 自增 | 只 `DUR` | 8 | `t+1 mod 175` | `DUR[i] − sec` | t 与 (i, sec) 成了两套独立计数，可能失步 |
| C 现状 | `START` + `END` | 16 | 直接读 `t` | `END[i] − t` | — |

推荐 **A**：

- `t_s = 索引数组(START,i) + sec`（2 个节点）——**复位只要清 `(i, sec)`，`t_s` 自动回到 0**，不用维护第三个计数器；
- `remain_s = DUR[i] − sec`（1 个节点，`n` 复用第 1 号节点的输出）；
- `slice_name = 索引数组(NAME,i)`，与 V3.1 相同。

换句话说：**把 `END` 换成 `DUR`**，表的数值总数不变，但语义从"结束秒"变成"片长"，与状态机一一对应。`END[i] = START[i] + DUR[i]` 仍成立，验收时可以对账。

> **已删了 `START` 怎么办**：补回 8 个数字即可（`0,46,50,76,80,140,145,170`，见《操作报告-V3.md》7.4.2）。`START` 不参与状态转移，只给 `t_s` 用，补它的成本远低于"两套计数器可能失步"的风险。

### 4.4 收益与风险

| 维度 | 查表法（现状） | 状态机法 | 评价 |
|---|---|---|---|
| 每 tick 运算量 | 扫 8 片（O(8)） | 一次比较（O(1)） | 状态机优 |
| 配时表规模 | `START`+`END` = 16 个数字 | `START`+`DUR` = 16 个数字 | 持平（语义更清楚） |
| 语义 | "t 落在哪片"（数学） | "到点切下一片"（工程） | 状态机更贴信号机 |
| 嵌套结构 | While 里套 For（有隧道自动索引的老坑） | **只有 While** | 状态机优 |
| 可扩展性 | 加全红/黄闪要重填整张表 | 加一个子状态即可 | 状态机优 |
| 复位/跳转 | 改 t 即可 | 要显式清 `(i, sec)` | 查表优 |
| 调试 | 可"跳到第 100 秒"看现象 | 只能连续跑 | 查表优 |
| 节点数 | ≈7（For 内 4 + 循环外 2~3） | ≈7 | **基本持平，别指望省节点** |
| 改动风险 | — | 换掉整个时间基准，验收要重跑 | 中 |

---

### 4.5 等价性：先在脚本里跑通，再去 LabVIEW 里搭

`verify_state_machine.py` 把上面这套状态机在 Python 里跑 175 拍，逐值比对 `完整灯态逐秒表.csv`：

```
周期 = 175 s，时长表 DUR = [46, 4, 26, 4, 60, 5, 25, 5]
自洽性检查：START[k] == sum(DUR[:k]) 全部成立 ✓
[通过] 2625 个值全部一致 —— 状态机方案与 V3.1 查表方案逐秒等价。
```

（2625 = 175 秒 ×（`t` + 片号 + `remain` + 12 只灯））。边界抽样：

```
片1→片2 边界 t=46: 前一拍 (t=45, 片1, sec=45) → 本拍 (t=46, 片2, sec=0)
片5→片6 边界 t=140: 前一拍 (t=139, 片5, sec=59) → 本拍 (t=140, 片6, sec=0)
```

**这条结论的用法**：设计本身没有逻辑漏洞，所以 LabVIEW 里一旦对不上，问题**必然在接线**（第 4/7 号 `选择` 没共用同一根条件、第 6 号取了商而不是余数、移位寄存器初值没给、`≥` 写成 `>`），排查范围立刻从"整段逻辑"缩到"4 个嫌疑点"。

---

### 4.6 真正的收益：可扩展性

节点数并不省（见 4.4），省的是"**以后要加功能时动不动结构**"。这是本路口真会遇到的四件事：

| 要加的功能 | 查表法要改什么 | 状态机要改什么 |
|---|---|---|
| **全红 R 秒**（每相位黄灯后清空） | 片数 8→12，重新生成 `START/END/NAME`，**重填 144 格 `COLOR`** | 转移里加一个"全红子状态"，`DUR` 加一列 |
| **黄闪 / 行人绿闪**（亚秒级闪烁） | 表里没有亚秒概念，**表达不了** | 加一个闪烁计数器 + 半秒节拍，状态多一位 |
| **感应控制 / 公交优先**（检测到车就提前结束绿灯） | `t→i` 是纯函数，**没法"提前跳"**，只能重写映射 | 检测信号直接置"推进?"为真，一个条件 |
| **多时段配时**（早高峰/平峰/夜间） | 每套配时要一整套 `START/END/COLOR`，还要按时间切换 | 准备多张 `DUR`，按当前时段选一张 |

一句话：**查表法是"把结果抄下来"，状态机是"把规则写下来"**。抄下来的结果改一次要重抄一遍；写下来的规则改一个数就行。

**为什么当初不让时间基准先换**：V3.1 改的是"数据长什么样"，`t`、`i`、片长、切换点全不变，所以能直接用现成的逐秒表验收；V3.2 改的是"时间怎么走"，一旦对不上，要先分清是计时错还是译码错。现在 V3.1 已验收通过，这个前提满足了。

## 5. 想法③：为什么不做（控件改造不单独设期）

结论先给：**控件层面没有值得单独做一期的收益**。三条依据：

1. **把 28 只灯打包成簇/数组不划算。** 每个布尔终究要连到一个端子上，打包只是把"端子在灯上"换成"端子在捆绑节点上"，还要多 12 个 `捆绑` + 1 个 `创建数组`，接线端子从 28 个涨到 **36 个**。

   | 做法 | 新增节点 | 新增接线端 | 面板控件数 |
   |---|---:|---:|---:|
   | 28 只单灯（现状） | 0 | 28 | 28 |
   | 簇数组（12 行 × 红/黄/绿） | 13 | **36** | 1 |
   | 二维布尔数组（12×3） | 2+ | **36** | 1 |

   **打包省的是"面板控件数"，花的是"框图连线数"**，而这块面板本来就不需要压缩。

2. **"操作类"控件只是演示便利。** 档位（1×/10×/50×）、复位按钮能减少演示时的手动输入，但不影响模型正确性、不影响验收、不改任何灯态。课程设计的评分点不在于"能不能一键快放"。

3. **零成本的"方便"已经做了。** 页①页②同名、统一配色、分组修饰、停止按钮「释放时锁存」这些都不需要新节点，V2/V3.1 的面板上已经具备，不需要另立一期。

> 所以控件改造不单独设期。它的价值上限是"演示时顺手一点"，成本却是重新连一批线、再改一轮面板；把时间投到 V3.2（时间基准）上，收益是结构性的。

## 8. 风险与边界

1. **V1/V2 不许动**。它们是基准与对照，V3 只在 `V3-优化/` 里改。
2. **逐秒表是唯一真值**。V3 任何一步改完都要能与 `完整灯态逐秒表.csv` 对上；对不上就是错，不要"看着像对"就算通过。
3. **`i` 的编码约定要写进注释/标签**（"偶数片=绿、奇数片=黄"）。这是方案 A 唯一的隐性知识，忘了就会看不懂自己搭的图。
4. **不要顺手改配时**。V3 的目的不是换方案，是换实现；`176 s`、`全红 R 秒` 之类的是另一件事（改 `gen_timing_table_v2.py` 的 `PHASES` 再重跑表）。
5. **方案 C 别落地**。位打包很好讲，但 84 个节点 + 不可读常量，会把你已经踩过的"数据错查不出来"问题放大。
